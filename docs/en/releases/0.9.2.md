# 0.9.2 — upgrading from 0.9.1

**Planned; not yet released.** These notes describe the changes proposed in [PR #46](https://github.com/ordo-systems/keen-proxy/pull/46), following [issue #39](https://github.com/ordo-systems/keen-proxy/issues/39).

[Version history](index.md) · [0.9.1 release notes](0.9.1.md)

## Firewall diagnostics

When `iptables-restore` fails, the diagnostic ZIP records the final exit code and whether `-w` was used. If restore reports a line number, it also records the table and operation, and the chain and target where applicable. For `COMMIT` failures it identifies the table, not a specific rule. Apply, rollback, and watchdog failures are recorded separately. The ZIP excludes raw stderr and rule arguments.

## TPROXY readiness and recovery

- The loopback readiness check reports `ready`, `unavailable`, or `unknown`. Confirmed unavailability blocks TPROXY before Apply changes interception. An inconclusive result allows Apply to proceed. OpenWrt with `iptables-nft` may report `unknown` because the legacy target list is incomplete.
- If saved TPROXY is confirmed unavailable at startup, the panel stays accessible without interception. KeenProxy neither explicitly loads the kernel module nor silently switches to REDIRECT.
- After fixing the reported problem, use loopback recovery over SSH to activate saved settings. The YAML and its `.previous` backup are preserved. [Keenetic TPROXY troubleshooting](../troubleshooting.md#keenetic-tproxy-apply)

## OpenWrt compatibility checks

CI exercises saved TPROXY startup and `TPROXY → REDIRECT → TPROXY` with real `iptables-nft` in OpenWrt 24.10.5 ARM64 userspace. It checks the firewall rules using Docker's Linux kernel, not OpenWrt firmware, and does not verify UDP forwarding.
