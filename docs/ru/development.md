# Разработка документации

## Локальная сборка

Потребуется Python 3.12+:

```sh
make docs-preview
```

Команда создаёт `.venv-docs`, собирает документацию в строгом режиме в `site/` и запускает сервер на порту 8097. Другой порт задаётся через `DOCS_PORT`. `make docs` только собирает сайт. Те же шаги вручную:

```sh
python3 -m venv .venv-docs
.venv-docs/bin/pip install -r requirements-docs.txt
DOCS_SITE_URL=http://localhost:8097/ .venv-docs/bin/mkdocs build --strict
python3 -m http.server 8097 --directory site
```

Откройте `http://localhost:8097/` для английского и `/ru/` для русского. Сервер раздаёт только статические файлы.

## Модули встроенного движка

После клонирования выполните `go mod download`; Git submodules не нужны. Корневой `go.mod` сохраняет upstream-пути импортов и закрепляет sing-box-lx `v1.14.4-lx.35` и соответствующие форки WireGuard/AWG, sing-tun, gVisor и uTLS пятью версионными директивами `replace`. Go не наследует `replace` зависимостей: все пять закреплений должны оставаться в корневом модуле и проверяться вместе при обновлении движка.

Для WireGuard/AWG закреплён коммит [форка Ordo Systems](https://github.com/ordo-systems/wireguard-go-awg2-lx), а не меняющаяся ветка. В сборках для роутеров очередь приёма использует буферы по размеру пакета, а слоты чтения UDP/GRO сохраняют исходную ёмкость. Это добавляет копирование на приёме, не меняя передачу. На платформах с ограниченным пулом приёма сохраняется исходный путь.

Makefile и CI выбирают Go **1.27.3** из директивы `go` корневого `go.mod`, сохраняя минимальную версию языка из main. Для прямых команд используйте `GOTOOLCHAIN=go1.27.3 go …`, если PATH выбирает другой компилятор. Не копируйте весь upstream-набор `LX_TAGS`: у KeenProxy свой сокращённый набор full/lite, без тегов, требующих `-checklinkname=0`.

Архив исходников релиза содержит манифесты модулей и скрипты сборки. При сборке загружаются точные версии, проверяемые через `go.sum`; инициализация Git submodules не требуется. Не заменяйте закрепления на `@latest`.

## Проверка регрессий памяти

Публичные локальные цели `make build`, `make build-router` и `make build-router-lite` требуют обеих проверок памяти до создания бинарников приложения, в том числе при параллельном make. Публичная локальная точка входа не обходит ни одну проверку. Цели только для CI `make build-router-ci` и `make build-router-lite-ci` собирают те же полные и облегчённые артефакты роутера и не запускают и не сертифицируют проверки памяти. Для самих проверок нужны Docker с правом запуска привилегированных контейнеров, Python 3, история Git и Go toolchain из `go.mod`. Для сравнения нужна фиксированная базовая ревизия. Отдельный запуск:

```sh
make memory-regression-unit
make memory-regression
make memory-stress
```

CI собирает артефакты роутера без обеих проверок:

```sh
make build-router-ci
make build-router-lite-ci
```

Эти цели не сертифицируют память. Не используйте их вместо публичных локальных целей, если бинарник должен пройти обе проверки.

Проверка собирает текущие исходники и фиксированную принятую базу из main `e6a1a1df2730418cf9edc2a71df4cec3e99be255` компилятором из текущего Makefile. База сохраняет полный набор тегов этой ревизии, включая AWG, XHTTP и встроенный TrustTunnel; кандидат получает актуальные теги полной сборки через `make memory-build-settings`. Оба демона получают одинаковую синтетическую конфигурацию с двумя WireGuard и одинаковую TCP/UDP-нагрузку, без роутера, рабочих ключей и внешних тестовых адресов. Изменения namespace и firewall остаются внутри одноразовых Linux-контейнеров с уникальным владельцем.

Эта база явно принимает нынешнее потребление памяти как исходный уровень для будущих регрессий. Это смена политики сравнения, а не исправление памяти или отмена сохранённых провалов относительно родителя PR #25. При смене базы пороги, число замеров и отдельный AWG stress с 320 МиБ оставались прежними; более позднее изменение абсолютного допуска описано ниже. Граница восстановления исторических релизов остаётся независимой ревизией до AWG, указанной ниже.

Этот предок из main содержит те же исходники приложения и параметры полной сборки, что принятая сборка `37d196c`; побайтовое совпадение ARM64-бинарников проверено с компилятором и флагами гейта. Неизменяемая база в истории main остаётся доступной после squash-merge и удаления PR-ветки без дополнительного тега и сетевого скачивания. Полная история репозитория по-прежнему обязательна.

Три парных запуска измеряют фазы покоя, нагрузки, освобождения TCP и повторных Apply. Под нагрузкой через оба туннеля идут параллельные TCP-потоки и проверенные UDP-пакеты. После закрытия TCP те же два UDP-сокета продолжают обмен во время замеров освобождённого состояния. Отсутствие TCP-потоков у клиента и сервера, свежие UDP-ответы и ровно одна сессия демона на туннель доказывают освобождение TCP; произвольные оставшиеся записи трекера не объявляются UDP. Замеры во время Apply учитывают временные пики RSS, а не только итоговое установившееся состояние. Сравниваются медианы RSS, анонимной RSS и наблюдаемого пика RSS каждой фазы. Рост больше `max(10% от базы, 12 МиБ)` проваливает проверку; равенство допускается. Отсутствующие замеры, неуспешные передачи, неполное освобождение TCP и ошибки Apply считаются ошибками, а не пропуском. Принудительные GC и освобождение страниц не меняют измеряемый процесс.

Абсолютный допуск явно увеличен с 8 до 12 МиБ по результатам A/A с идентичными бинарниками: два из десяти сравнений на родном ARM64 ложно провалились по анонимной RSS после Apply, максимальная положительная разница — 9,62 МиБ; отдельное сравнение GitHub AMD64 провалилось по той же фазе и метрике при 9,42 МиБ. Исходные отчёты сохранены. Допуск 12 МиБ даёт запас относительно этих наблюдений, но не является статистически установленной границей шума. Допустимый рост увеличивается не более чем на 4 МиБ; это не исправление памяти и не гарантия отсутствия ложных срабатываний. Пересчёт тех же входных данных — оценка постфактум, а не независимая калибровка. Относительный допуск 10%, медианы трёх запусков, база, нагрузка и отдельные лимиты AWG 320/384 МиБ не меняются.

Отдельный AWG-сценарий только для кандидата доказывает передачу трафика и записывает память. Он не входит в медианы общего WireGuard-сравнения, хотя принятая база тоже поддерживает AWG. Это сохраняет разделение общей нагрузки WireGuard и AWG smoke-сценария; это не непрерывная проверка ниже.

Отчёты, исходные замеры, подтверждение передачи данных, журналы и идентификаторы сборок сохраняются в `.agents-work/memory-regression/`. **Memory regression** загружает эти данные сравнения даже при провале задания. Каждое задание AWG stress загружает собственный артефакт `awg-stress-<run>-<attempt>-<arch>` с тем же составом данных, включая провалы. **Router builds** не загружает данные памяти. Перед изменением порога или базы изучите отчёт; нельзя увеличивать бюджет только ради зелёной проверки. Смена порога или базы требует отдельного обоснования и замеров до и после.

Стенд работает на родной Linux-архитектуре Docker-сервера. Результаты не сертифицируют ARM64/MIPS-устройства, отсутствие длительной утечки или безопасность DNS. Измеряется полный демон с рабочим набором протоколов, но без встроенных UI-ресурсов; кросс-сборки роутера по-прежнему включают обычный интерфейс. Публичные локальные команды сборки не обходят ни одну проверку при недоступном Docker. Цели роутера только для CI собирают без этих проверок и не заменяют их локально.

### Длительность и расхождение замеров между хостами

Гейты локальной сборки обязательны: публичные цели `make build`, `make build-router` и `make build-router-lite` останавливаются при ошибке, в том числе при параллельном make. CI больше не связывает эти проверки со сборкой роутера; независимые задания описаны ниже, рядом с проверкой стресса. Файлы релиза из помеченного исходника по-прежнему проходят обе проверки до публичных целей роутера. Успешный последовательный запуск включает не менее 5 минут 21 секунды замеров и пауз Apply: семь сравнительных сценариев по 38 секунд и 55 секунд фаз стресса. Компиляция базы, кандидата и сервера, скачивания, сборка образов, запуск, ожидание освобождения соединений, передача владельца данных, сборка интерфейса и кросс-сборки добавляют время; холодный запуск дольше. Это нижняя граница последовательного выполнения, а не гарантия срока завершения. Для сопоставимых замеров избегайте параллельного make и конкурирующей нагрузки на CPU/память; предпочтителен контролируемый Linux-хост сборки.

Если локальное сравнение провалилось, а задание **Memory regression** прошло:

1. Остановите сборку и сохраните `report.json`, исходные фазовые замеры, журналы и манифест этого запуска. Успех CI не отменяет локальную ошибку.
2. Сопоставьте идентификаторы исходников и бинарников, версии Go, теги протоколов, архитектуры Docker и ограничения ресурсов. Зафиксируйте нагрузку на CPU/память хоста и другие задачи; разные архитектуры и окружения — отдельные наблюдения, а не взаимозаменяемые повторы.
3. Исследуйте проваленную фазу и отличите воспроизводимый рост от установленной причины в окружении. После исправления такой причины запишите отдельный замер, сохранив исходную ошибку и объяснение. Не повторяйте запуск только ради успеха, не форсируйте GC и не меняйте пороги или базу ради сокрытия результата.
4. Если расхождение не объяснено, оставьте локальную сборку заблокированной и разберите данные. Не обходите локальный гейт через `-o`, `build-router-ci`, `build-router-lite-ci`, прямые команды сборки или ранее успешный результат CI. Успех **Router builds** не сертифицирует память.

### Непрерывная проверка AWG

`make memory-stress` (`sh test/memory/run.sh --stress`) — отдельная проверка. Она собирает только текущий демон и тестовый сервер, копирует стенд и не архивирует, не собирает и не запускает базу сравнения. Результат не подаётся в отчёт сравнения.

Контейнер имеет уникального владельца, `--network none` и привилегированный режим, чтобы стенд создал собственные namespace. Пределы: 2 ГиБ памяти без swap, квота 2 CPU и привязка `0-1`. Родительский процесс контейнера получает `GOMAXPROCS=2`, `GOGC=100` и `GOMEMLIMIT=off`. Предел Go 320 МиБ действует только на измеряемый демон внутри стенда; это мягкий бюджет, а не настройка продукта по умолчанию и не потолок RSS. В память контейнера входит и синтетический удалённый сервер. Если Docker сообщает меньше 2 CPU, запуск завершается ошибкой и не снижает привязку или квоту. До старта сценарий проверяет фактически применённые память, swap, CPU, привязку, сеть и окружение родителя; несовпадение — ошибка.

Стенд создаёт 32 непрерывно продвигающихся TCP-потока через первый туннель AWG с MTU 1280 и `S4=12`; второй обычный туннель WG остаётся без нагрузки. Измеряются 5 секунд простоя, 30 секунд нагрузки и 20 секунд после того, как демон и сервер сообщат об отсутствии соединений. Проверенное эхо должно достигать не меньше 50 Мбит/с за фактическое окно нагрузки, а RSS и максимум `VmHWM` за жизнь процесса — оставаться ниже 384 МиБ. Остановка потоков, слишком низкая нагрузка, достижение порога и ошибка очистки проваливают проверку. Повтора и принудительного GC нет. Данные остаются в `.agents-work/memory-regression/` даже при провале. Принадлежащие контейнеры и образы удаляются при любом выходе; если скопировать временные файлы из контейнера не удалось, этот предел сообщается, а контейнер всё равно удаляется.

Скорость рассчитывается по времени публикации тех же двух снимков счётчиков; фазы памяти и CPU сохраняют собственную длительность. Экспортируемые данные сохраняют закрытые права доступа и передаются UID/GID пользователя хоста только после подтверждения остановки нагрузки. Ограниченный вспомогательный контейнер учитывается отдельно и монтирует только каталоги данных этого запуска; ошибка передачи владельца проваливает проверку, но не прерывает очистку ресурсов.

Локальные `make build`, `make build-router` и `make build-router-lite` запускают и эту проверку, и `make memory-regression`. CI больше не связывает эти проверки со сборкой роутера и не использует `make -o`. Независимые задания выполняются на отдельных раннерах. Провал одного не отменяет остальные.

- **Memory regression** выполняет `make memory-regression` с полной историей Git и загружает данные сравнения даже при провале задания.
- **AWG stress (320 MiB)** и **AWG stress ARM64 (320 MiB)** запускают `make memory-stress` на нативных раннерах GitHub для AMD64 и ARM64. Каждое задание сохраняет свой отчёт и должно пройти перед сборкой релизных пакетов.
- **Router builds** выполняет `make build-router-ci build-router-lite-ci` с Go и Node. Оно не запускает нагрузки памяти, не загружает данные памяти и не сертифицирует память.

**Tests and builds** и **Network integration** не меняются. Успех **Router builds** не является результатом проверки памяти.

**OpenWrt TPROXY integration** (`make integration-openwrt`) запускает ARM64-демон в Docker с пользовательским окружением OpenWrt 24.10.5 и настоящим `iptables-nft`. Проверяются старт с сохранённым TPROXY, переключение на REDIRECT и обратно, а также наличие перехода и правила TPROXY в ядре. Нужны Docker на ARM64, `NET_ADMIN` и поддержка nftables/TPROXY. Тест использует ядро Linux, на котором работает Docker, а не ядро прошивки OpenWrt, и не проверяет пересылку UDP.

**Проверка обновления Entware** (`make integration-entware`) устанавливает официальные пакеты Entware для ARM64 в одноразовый контейнер Debian и запускает защищённый bootstrap с опубликованной версией 0.9.2 и локальной сборкой. Проверки реальными пакетами IPv4 и IPv6 подтверждают блокировку транзита до запуска службы и его восстановление после успешного обновления или автоматического отката. Доступ к роутеру из LAN сохраняется. Тест использует штатный `S99keenproxy`. Нужны привилегированный контейнер Docker на ARM64 и поддержка legacy Netfilter для IPv4 и IPv6. Проверяется ядро Linux, на котором работает Docker, а не ядро прошивки Keenetic.

Для помеченного исходника вне исторического восстановления задание файлов релиза отдельно выполняет `make memory-stress` и `make memory-regression`, затем `make -o memory-stress -o memory-regression build-router build-router-lite` с прежними аргументами идентификатора релиза. Оба флага `-o` допустимы только после успеха соответствующего шага в том же задании. `-o` GNU make помечает эти служебные цели уже выполненными, чтобы публичные цели не повторяли проверки. Публичные цели нужны, потому что более старые теги с AWG не определяют имена только для CI. Отсутствующая цель проверки завершается ошибкой и никогда не выбирает историческое восстановление. `-o` — не обход через переменную окружения, не кэш и не локальный ярлык. Не используйте его, если оба отдельных шага только что не завершились успехом в том же задании.

Процесс выпуска LokiVPN проверяет исходники по тегу версии. Независимые задания CI проходят до сборки пакетов. Задание сборки также выполняет обе проверки памяти перед сборкой бинарников. Защита ветки настраивается отдельно. [Порядок выпуска](https://github.com/LokiVPN/keen-proxy/blob/master/RELEASING.md#build-a-lokivpn-release)

Восстановление файлов исторического релиза из `main` явно ограничено Git-предками фиксированной базы до AWG `9d398fb3754036cbe35df1cf07098164ff62a9d5` и самой этой базой, включая `v0.8.0`. CI текущего workflow остаётся обязательным, а версия тега проверяется до дорогих операций. Восстановление не изменяет исходники тега и использует его исходный Makefile и флаги протоколов для тестов Go, vet, сетевой интеграции, тестов интерфейса и полной/облегчённой сборок роутера с идентификатором выбранного релиза. Явное уведомление и загружаемые манифест, журнал команд и код завершения в `.agents-work/release-legacy/<run>-<attempt>/` фиксируют этот отдельный договор проверки, в том числе при ошибке; это не замеры памяти и не сертификация AWG, поскольку эти исходники не поддерживают AWG. Коммиты вне указанной цепочки предков обязаны пройти обе проверки памяти; отсутствие целей приводит к ошибке, а не выбору восстановления. До публикации недостающих файлов существующие файлы должны побайтово совпасть. См. [RELEASING](https://github.com/ordo-systems/keen-proxy/blob/main/RELEASING.md#github-setup-and-recovery).

## Редактирование и переводы

Поддерживайте одинаковые Markdown-файлы в `docs/en/` и `docs/ru/`. Навигация задаётся в `mkdocs.yml`; i18n-плагин добавляет переключение языка, перевод навигации и поиск. Скриншоты на обоих языках сохраняйте в `docs/assets/screenshots/`. Снимайте только синтетические сеансы и обновляйте подписи при изменении экранов.

## Прототип WebUI KeeneticOS

Локальные стенды в `test/keenetic-webui/` добавляют нативный маршрут KeenProxy
в проверенный Angular-бандл KN-3812 в памяти. Они проверяют штатное боковое меню,
вход, роли и диалог несохранённого черновика на синтетических ответах HTTP и RCI.
Рабочая страница на штатном адресе роутера потребует отдельной схемы доступа
и авторизации API.

Для сценариев поведения нужны Python 3.10 или новее и Chromium headless shell.
Укажите свой бандл поддерживаемой версии WebUI и закреплённый браузерный файл
[Zone.js 0.15.1](https://cdn.jsdelivr.net/npm/zone.js@0.15.1/bundles/zone.umd.min.js).
Скрипт проверяет хэши обоих файлов. Для контрольного прогона исходного меню
добавьте `--baseline`.

```sh
python3 -B test/keenetic-webui/full_bootstrap.py \
  --bundle /path/to/main.js \
  --zone-js /path/to/zone.umd.min.js \
  --browser /path/to/chrome-headless-shell
```

Для скриншотов в Orca установите `PySquashfsImage==0.9.0` в изолированном
окружении Python и возьмите стабильный образ KN-3812 5.1.10 из
[официального архива прошивок](https://osvault.keenetic.net/KN-3812/5.01/).
Стенд сверяет хэши прошивки и WebUI и выводит адреса исходной панели, панели
администратора и панели для чтения. Для сравнения меню OPKG откройте исходный
и административный адреса с одинаковым размером окна и темой. Стили,
иконки и шрифты берутся из того же архива.

```sh
python3 -B test/keenetic-webui/orca_fixture.py \
  --firmware /path/to/KN-3812_stable_5.1.10_5.01.C.10.0-0.bin
```

### Карточка KeenProxy в «Приложениях»

Локальный стенд загружает скрипт и стили из `tools/keenetic-webui/` вместе
со штатными ресурсами KeeneticOS 5.1.10. Карточка занимает первую колонку
сетки «Приложения» на странице `/apps` и открывает текущую панель
KeenProxy. Она следует раскладке штатной сетки и остаётся доступной, когда
список штатных приложений пуст. По умолчанию ссылка ведёт на HTTP-порт 8086
текущего хоста. Для другого адреса панели задайте абсолютный URL с HTTP
или HTTPS в атрибуте `data-keenproxy-panel-url` элемента скрипта.

Запустите стенд с `--applications-card`, чтобы сравнить штатную страницу
и страницу с карточкой. Параметр `--panel-url` задаёт адрес для проверки.

```sh
python3 -B test/keenetic-webui/orca_fixture.py \
  --firmware /path/to/KN-3812_stable_5.1.10_5.01.C.10.0-0.bin \
  --applications-card --panel-url http://127.0.0.1:8086/
```

### Пакет Entware для KN-3812

Соберите отдельный пакет карточки с помощью Python 3.

```sh
python3 tools/keenetic-webui/build-ipk.py .agents-work/keenetic-app-card
```

Скопируйте полученный файл `keenproxy-app-card_0.1.0-1_all.ipk` на роутер.
Выполните команду в оболочке Entware, указав путь к копии файла.

```sh
opkg install /path/to/keenproxy-app-card_0.1.0-1_all.ipk
```

Откройте **Приложения** по обычному адресу KeeneticOS и нажмите
**Открыть панель** на карточке KeenProxy. Ссылка ведёт в работающую панель
на порту 8086. Веб-интерфейс загружает сборки Angular из прошивки.
При установке и запуске Entware пакет сверяет контрольные суммы HTML, JavaScript и стилей
KN-3812 stable 5.1.10 (`5.01.C.10.0-0`), затем подключает HTML с двумя
ресурсами карточки через bind-mount. Если контрольные суммы изменятся,
роутер покажет штатную страницу.

Команда `opkg remove keenproxy-app-card` удаляет карточку и возвращает
штатную страницу.

### Вход через KeeneticOS { #keenetic-auth }

В KeeneticOS вход включён по умолчанию. KeenProxy берёт адрес из первого
частного IPv4-адреса LAN-интерфейса (`lan.interface`, по умолчанию `br0`).
Браузеру подходит LAN-адрес IPv4 роутера или `my.keenetic.net`, оба с портом
панели (порт 80 не указывается); любой другой `Host` отклоняется. Чтобы
задать адрес вручную, передайте `-keenetic-auth-origin http://ROUTER_LAN_IP`
или переменную `KEENPROXY_KEENETIC_AUTH_ORIGIN`; `-keenetic-auth-origin=off`
отключает вход. В Entware такую настройку можно сохранить между запусками и
обновлениями в необязательном файле `/opt/etc/keenproxy/keenproxy.env`,
например `KEENPROXY_KEENETIC_AUTH_ORIGIN=off`: `/opt/etc/init.d/S99keenproxy`
подключает его как shell-скрипт при каждом запуске, а обновление и удаление
его сохраняют. Если при запуске у LAN-интерфейса нет IPv4-адреса, демон и
маршрутизация всё равно запускаются, в журнал пишется одна ошибка, а запросы
не с loopback получают `503` до перезапуска. Для входа `api.listen` должен
иметь пустой хост, `0.0.0.0`, `::` или LAN-адрес IPv4. Если адрес нельзя
использовать, выведенный или заданный явно (например при `api.listen`
`127.0.0.1:8086`), включается описанный выше режим 503, а в системный журнал
пишется ошибка; loopback продолжает работать. Режим рассчитан на локальный
протокол HTTP-сеансов KeeneticOS 5.1.10.

KeenProxy проверяет действующий сеанс и права учётной записи для каждого
запроса страницы. Администратор (права на веб-интерфейс и командную строку)
может просматривать и менять настройки. Учётки только для чтения и
менеджеры могут только просматривать: запись получает
`403 KeeneticOS management access denied`. Остальные учётки и деморежим
получают отказ. При выходе из любой панели сеанс роутера завершается.

Сеанс открывает только страницы. В `/api` ему доступны лишь
`GET /api/session` и `POST /api/logout`: настройки, ключи и журналы остаются
за loopback-[управляющим API](#control-api), а страницы, когда появятся,
покажут их на стороне сервера. Вход — единственный способ доступа не с
loopback: без него остальные клиенты получают `403 local access only`.

Восстановление доступа и системы без KeeneticOS: пробросьте панель через SSH
и откройте её на loopback, которому всегда доверяют:

```sh
ssh -L 8086:127.0.0.1:8086 root@ROUTER
# затем откройте http://127.0.0.1:8086
```

В OpenWrt и других системах без KeeneticOS вход выключен, поэтому панель
доступна только через такой туннель.

## Управляющий API { #control-api }

HTTP API — управляющий, а не API браузерных сеансов. Запрос с loopback-адреса
(`RemoteAddr`) и заголовком `Host` `127.0.0.1`, `::1` или `localhost` (любой
порт) принимается без токена; loopback-запрос с другим `Host` считается запросом
из LAN. На это опираются проверка памяти
(`test/memory/scenario.py`), `make integration` (`test/netns/run.sh`) и
локальные скрипты на роутере; установщик API не вызывает. Заголовок
`Authorization`, который клиент ещё отправляет, игнорируется. Любой другой
клиент получает в `/api` ответ `403 local access only` с сеансом KeeneticOS
или без него (`503`, пока вход недоступен); браузерам отвечают только
`GET /api/session` и `POST /api/logout`, поэтому учётка только для чтения
никогда не получает адреса подписок, ключи и записи журналов. Один
промежуточный обработчик проверяет каждый путь, включая страницы; без
проверки проходят только эти два маршрута.

Ещё до решения о доверии этот обработчик отклоняет запись с другого источника
ответом `403 cross-origin request denied`: любой метод, кроме `GET`, `HEAD` и
`OPTIONS`, у которого `Sec-Fetch-Site` не равен `same-origin` или `none` либо
`Origin` не совпадает с `Host`. Правило действует и для loopback, и для
сеансов KeeneticOS, поэтому страница, открытая при работающем SSH-туннеле,
не может через него менять настройки. Клиентов без этих заголовков, например
curl и тестовые проверки, правило не затрагивает.

Остаточный риск: прокси, запущенный на роутере (tinyproxy, xray и подобные),
который подключается с `127.0.0.1` и `Host: 127.0.0.1:<порт>`, считается
доверенным. Не запускайте открытые локальные прокси рядом с KeenProxy.

Токен панели, параметр `-key`, доверенные сети и `POST /api/login` удалены;
`api.token_file` и `api.no_token_from` принимаются и игнорируются. Панель на Vue
и демо-режим тоже удалены. Пока не появится серверный интерфейс, `GET /` и
другие пути вне `/api/` возвращают `503 KeenProxy interface is being rebuilt`
доверенным loopback-клиентам и вошедшим учёткам KeeneticOS; остальные клиенты
получают тот же отказ, что и от API (`401`, `403` или `503`), коротким текстом. Журнал остаётся внутренним (`GET /api/journal/{kind}` с loopback и
ZIP для поддержки); поток и экспорт журнала, пресеты, обмен ресурсами, списки
фильтрации рекламы, GeoIP-поиск, предпросмотр доменов, импорт и экспорт YAML и
проверка DNS удалены.

## Схема конфигурации 2 и откат { #config-schema }

Новые конфигурации записываются с `schema_version: 2`.

- Файл schema 1, который ещё читается, используется как есть. Перед первой
  записью он копируется байт в байт в `config.v1.yaml` (права 0600, никогда не
  перезаписывается; если файл есть, берётся имя с отметкой времени). Заготовки
  установщика, где на верхнем уровне есть только `schema_version`, `lan` и
  `api`, не копируются.
- Файл schema 1 или нечитаемый файл, который больше не читается, при запуске
  сбрасывается в памяти: сохраняются `api.listen`, `lan` и первая корректная
  подписка, остальное берётся по умолчанию. Сам файл при запуске не меняется.
  Первое сохранение копирует его байт в байт в `config.v1.yaml` (кроме файла
  только со стартовыми настройками установщика) и только затем
  записывает schema 2. Поэтому при откате обновления до первого сохранения
  старый релиз читает свой файл, а каждый перезапуск до этого момента
  вычисляет тот же сброс. Повреждённый файл schema 2 по-прежнему вызывает
  ошибку: демон не запускается, а журнал называет только файл, потому что
  текст ошибки может содержать учётные данные. Чтобы увидеть ошибку в
  терминале, выполните на роутере `keenproxy -dry-run -config <path>`.
  `-dry-run` и `--url` используют сброс, ничего не записывая.
- `tools/bootstrap.sh` этого релиза также делает снимок конфигурации перед
  установкой и восстанавливает его при неудачном обновлении. Если целевая
  версия вообще не читает schema 2, установщик атомарно переключается на
  новейший сохранённый `config.v1*.yaml`, а новый файл оставляет как
  `config.v2*.yaml`. Версию, которая читает schema 2, но отклоняет файл,
  установщик не ставит и ничего не меняет. После чистой установки этого релиза
  резервной копии v1 нет, поэтому откат на более старый релиз отклоняется при
  проверке и ничего не меняет.
